## 3. The 60-second story (what an interviewer actually hears)

1. **The problem** — Most forecasting demos show a fitted line and stop. Nobody asks: is the data any good, which model is actually best *out-of-sample*, how confident are we, and — so what? A number is not a decision.
2. **The system** — A full pipeline: upload/validate (Data Quality Score) → EDA (trend, weekly+yearly seasonality, volatility, anomalies) → leakage-safe features → **expanding-window backtest** over 5 model families → retrain winner → forecast with prediction intervals → driver explanation → decision brief.
3. **The proof** — Real numbers from the live pipeline: ARIMA wins on sMAPE 11.35% across 4 chronological folds of 1,095 days. The brief turns that into an action ("demand is projected −2.6%… plan conservative restocking"). No hand-picked results — it's the committed dataset.
4. **The honest-eval point** — Models are selected by out-of-sample backtesting on *future* data, never a random split; naive baselines are always included, which is how you know ML actually added value.

## 4. Core talking points (pick 3–4, go deep)

- **Honest evaluation over headline accuracy.** The winner is chosen by expanding-window backtesting (4 chronological folds, ranking on sMAPE) — and a *seasonal naive* baseline comes within 1pp of the "fancy" ML model. That discipline is the signal: I don't cherry-pick results.
- **Model selection is a fair fight.** All five families share identical folds, horizons, and training windows (naive, seasonal naive, ETS, auto-SARIMA, XGBoost). Selection metric is configurable; the default sMAPE is symmetric and scale-free.
- **Uncertainty is shipped, not skipped.** Every forecast returns lower/upper intervals (native where available; a documented approximation otherwise) that widen with horizon. The decision brief treats the band's midpoint as the expectation — planning against the lower-middle of the range is the conservative play.
- **Nothing is silently modified.** The validator reports every issue (missing dates, gaps, duplicates, outliers, constant series) into an explicit issue list; the preprocessor logs every transformation. Reproducibility by design.
- **Explainability + decision layer.** Drivers (trend/seasonality/volatility), feature importance, SHAP opt-in — and a brief that's `generated_by: rule-based` by default (completely deterministic, no credentials). LLM is an opt-in feature flag so the project runs offline with zero keys.
- **Productized delivery.** FastAPI with OpenAPI docs, a Streamlit dashboard running the pipeline in-process, Docker Compose, 74 tests, and a free-tier Render blueprint for two public services.

## 6. Likely questions — STAR-style answers

### Behavioral / project questions

**Q: "Walk me through this project — what was your goal?"**
> "Most forecasting portfolio work stops at 'here's a model with a plot.' I wanted a *system*: validate the data, prove which model wins out-of-sample, quantify uncertainty, explain the drivers, and convert it into an actionable recommendation. And I wanted it reproducible — so I automated EDA, made every transformation reported, and shipped tests and a running dashboard."

**Q: "What was the hardest part?"**
> "Honest model comparison and uncertainty. It's easy to fit five models and show the prettiest lines. The hard part is a *fair* evaluation — identical expanding-window folds across every family — and honest intervals. A fun finding: a seasonal-naive baseline scored 12.3% sMAPE against 11.4% for auto-SARIMA and 12.5% for XGBoost. If I'd omitted baseline models, nobody would've known the ML was only marginally better. That's the discipline that projects usually skip."

**Q: "What would you do differently / next?"**
> "Real (non-synthetic) data in production, drift monitoring with scheduled retraining, model versioning/persistence, and a deep-learning or foundation-model forecasting comparison for longer horizons. The architecture is structured so those slot in without changing the pipeline contract."

**Q: "Why this problem?"**
> "Forecasting appears in inventory, revenue, capacity, energy, marketing — but teams drown in metrics that never make a decision. The value is turning a forecast into a defensible plan: a number nobody trusts is useless. This project therefore covers the full loop rather than only model fitting."

### Technical questions (go as deep or as shallow as the interviewer wants)

**Q: "How do you prevent data leakage?"**
> "Three rules: no random splits — evaluation is chronological expanding-window backtesting; features (lag k, rolling windows) are computed with a minimum lag of 1 so value at time t never uses information from t or later; and calendar features are used instead of indices. The backtest trains on the past and evaluates only on the future."

**Q: "Why expanding-window backtesting instead of a random split?"**
> "Time series is ordered — a random split leaks the future into training and inflates scores. Expanding window trains on growing history and evaluates on the next untouched block, which is the closest cheap proxy for 'predict the future.' Four folds over 1,095 days with a 60% initial train and 14-day horizons per fold."

**Q: "Why these five models?"**
> "They triangulate: naive/seasonal-naive are the *honesty baselines* (if ML can't beat them, don't ship ML); ETS and auto-SARIMA are the statistical workhorses with native seasonality; XGBoost on lag/rolling/calendar features is the ML candidate with recursive multi-step forecasting and feature importance. Best chosen on the backtest metric."

**Q: "How does the uncertainty / prediction interval work?"**
> "ETS and SARIMA emit native forecast intervals from their error structure; XGBoost gets a documented approximation (historical error quantiles scaled to the horizon), and the intervals are constructed to widen as the horizon grows. The API returns lower/upper arrays alongside the point forecast, and the brief labels them as the plausible planning range, not a guarantee."

**Q: "How does the decision layer work?"**
> "By default it's 100% deterministic: it takes the forecast (mean, end value, direction), the uncertainty (lower/upper means), EDA results (trend, seasonality strength, volatility), and the backtest metrics, and assembles a structured brief — forecast summary, risk assessment, and a business recommendation with concrete planning guidance. `generated_by: rule-based`. If `AI_ENABLED=true` *and* an API key is present, an LLM layer renders the same structured input with an always-on rule-based fallback. No credentials needed to run."

**Q: "Why FastAPI + Streamlit separately?"**
> "FastAPI is the service boundary — typed (Pydantic) requests/responses, OpenAPI docs, reusable by any client. Streamlit is the human interface; the dashboard runs the pipeline in-process so it works standalone, and it also demonstrates how a separate frontend would consume the API. Two surfaces, one pipeline."

**Q: "How do you test it?"**
> "74 tests across data validation, feature math, model behavior, evaluation/backtest, the orchestration pipeline, and the API (test client + TestClient). Deterministic pipeline and seeded data make assertions exact. Tests include the boundary case we actually fixed in production — fold allocation overshooting the series end → 500 error."

**Q: "How would this run in production?"**
> "The sample dataset swaps for real data via the upload endpoint or a database-backed loader; scheduled retraining + drift detection; the FastAPI service behind a load balancer; Streamlit served for analysts. The Render blueprint already provisions both services from the same Docker image."

## 7. Honest limitations (say these unprompted — builds trust)

- **Synthetic data** — the sample comes from a business-demand generator (seed 42); real CSV/XLSX can be uploaded, but all validation was run on generated demand.
- **Forecasts are probabilistic expectations, not causation** — driver signals are statistical association; no causal analysis is performed.
- **Recursive multi-step forecasting compounds error** — XGBoost builds the horizon step-by-step in an open loop; long horizons are less certain by construction.
- **Intervals are approximations where the model has no native uncertainty** — documented, not hidden, and every interval is labeled as a planning range.
- **Classic ML only** — deliberately no deep learning / foundation-model forecasting yet.

Why say them: an interviewer who probes will find them anyway (they're in the README). Framing them yourself shows self-awareness and honesty — a strong signal.
